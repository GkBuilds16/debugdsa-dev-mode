# Deployment and limitations

Run backend and frontend as separate processes; configure the ingress to serve the frontend and proxy `/api/*` to Express. Set `MONGODB_URI`, `FRONTEND_ORIGIN`, and production JWT settings in the deployment secret manager. Production startup requires JWT mode and a secret of at least 32 bytes. TLS should terminate at the platform ingress. Use a database account scoped to the Dev Mode collections and review indexes before rollout.

Known limitations: ZIP upload is implemented with bounded local parsing but has not been exercised against a live deployment; GitHub import validates URLs but deliberately returns 501 and does not fetch repositories. Creator source, candidate workspace changes, and immutable submission snapshots are stored on local disk, not shared/object storage; deployments need durable storage and a storage adapter before horizontal scaling. Database and filesystem operations are not transactional and orphan cleanup is not implemented. MongoDB connectivity and index creation were not verified, so run duplicate-active-attempt cleanup before deploying the new unique partial index. There is no evaluation sandbox; submissions remain `NOT_EVALUATED` with no score or feedback. Battle creation/management UI, battle completion scheduler, final ranking, and Socket.IO room are not implemented. Registration deadline, uniqueness, and capacity reservation are enforced server-side; live state transitions are not automated. No mock result is described as code execution.
