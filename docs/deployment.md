# Deployment and limitations

Run backend and frontend as separate processes; configure the ingress to serve the frontend and proxy `/api/*` to Express. Set `MONGODB_URI`, `FRONTEND_ORIGIN`, and production JWT settings in the deployment secret manager. Production startup requires JWT mode and a secret of at least 32 bytes. TLS should terminate at the platform ingress. Use a database account scoped to the Dev Mode collections and review indexes before rollout.

Known limitations: ZIP upload has bounded local parsing but has not been exercised against a live deployment; GitHub import validates URLs but deliberately returns 501 and does not fetch repositories. Creator source, candidate workspace overrides, candidate submission snapshots, battle workspace overrides, and battle submissions use private local disk, not shared/object storage. Deployments need durable storage before horizontal scaling. MongoDB connectivity and index creation were not verified. Run duplicate registration/attempt checks and review legacy battle records without version references before applying new indexes or using existing battle data. The server recovers battle states at startup and every 15 seconds, but transitions are not backed by an external durable job queue. Registration reservation and local-file/database coordination are not transactional and orphan cleanup is not implemented. There is no evaluation sandbox; submissions remain `NOT_EVALUATED`, with no score, feedback, or ranking. Battle state uses REST polling; Socket.IO is not integrated. `REGISTRATION_CLOSED`, `LIVE`, and `COMPLETED` are persisted from server times; `SUBMISSION_CLOSED` and `EVALUATING` are reserved states and are skipped while evaluation is unavailable.
